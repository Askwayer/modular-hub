# AI 网关需求迭代计划

版本：0.1 草案 · 日期：2026-11-13 · 当前状态：文档已起草，M0 待人工验收，开发尚未开始。

本计划以 [PRD](02-prd.md) 为范围基线。里程碑是用户要求的人工验收点：提交可复核的交付物和证据后，由用户选择通过、限范围通过或退回。不得将自动测试通过等同于人工验收完成。

## 1. 迭代顺序

```mermaid
flowchart LR
    M0[M0 需求与架构] --> M1[M1 转发与性能基线]
    M1 --> M2[M2 课题 / 公司 / 健康]
    M2 --> M3[M3 稳定性与用量闭环]
    M3 --> M4[M4 单公司试点]
    M4 --> M5[M5 跨公司推广验证]
    M5 --> M6[M6 生产验收]
```

优先投入转发与稳定性，不先建设完整管理界面。M1 用配置驱动最小实验；M2/M3 补齐正式契约；M4 再用最小管理页打通真实业务闭环。

| 迭代 | 主要任务 | 可审查交付物 | 人工关口 | 估算投入 |
| --- | --- | --- | --- | --- |
| I0 范围冻结 | 确认课题/公司身份、协议范围、试点和测试预算；登记架构决策 | PRD 签字版本、决策记录、待决项负责人 | **M0** | 1–2 人日 |
| I1 最小转发 | 新建独立 Java 模块；连接池、JSON/SSE、超时取消、模拟上游、真实模型基线 | 可执行 JAR、依赖树、协议样本、压测脚本与原始数据、目标环境启动记录 | **M1** | 4–6 人日 |
| I2 授权与健康 | 课题 Key、公司推广、部署身份、模型权限；版本化策略；三层模型健康 | 契约/数据设计、迁移脚本、身份测试、健康故障演示 | **M2** | 5–8 人日 |
| I3 稳定性与统计 | 多实例准入、租约、事件暂存/幂等重放、用量聚合、熔断、停机与故障恢复 | 24 小时报告、故障矩阵、完整功能性能报告、统计核对与缺口报告 | **M3** | 6–9 人日 |
| I4 单公司试点 | 最小管理页面、审批/推广/Key 操作、真实业务接入清单、小流量切换、回滚 | 接入说明、试点记录、操作审计、回滚演练和数据核对 | **M4** | 4–6 人日 |
| I5 跨公司推广 | 同课题接公司 B；隔离、汇总权限、独立停用、并发公平性 | A/B 公司对照报表、多部署接入记录、越权与共享进程测试 | **M5** | 2–4 人日 |
| I6 生产准备 | 72 小时持续运行、目标容量压测、双实例切换、备份恢复、依赖与制品检查 | 发布候选包、完整报告、运维手册、推广与回滚计划 | **M6** | 3–5 人日，另需持续运行观察窗口 |

合计约 25–40 人日，是范围内的初步估算，不是交付日期承诺。假设一名后端主力、前端按需参与，并有业务和运维提供测试环境；组织权限补建、证书设施、协议特殊适配与验收等待可能增加投入。可并行准备合成样本和运维清单，但依赖前一关口的实现及真实流量推广须等验收结果。

## 2. 各阶段的实施要点

### I0：先决定验什么

- 冻结 Java 非阻塞转发方向和独立应用边界；记录这是待实测的选择，不写虚构的 Python 对比结果。
- 选择试点课题和公司 A，列出公司 B 的后续推广场景。
- 确认公司身份方案、授权角色、源公司名录、模型兼容矩阵及测试环境。
- 确认额外延迟、吞吐、数据保留、轮换和离线策略目标。对未定容量先安排 M1 测量，不编造绝对 QPS。

### I1：技术可行性优先

- 在 Maven 父工程新增候选模块，沿用 JDK 17 与版本基线；不依赖全部 `vita-common`，不导入部门业务。
- 同步后端规范中的独立网关边界及 `/v1/*` 协议例外；其他管理接口保持现有规则。
- 实现普通 JSON、逐段 SSE、连接池、缓冲上限、超时、取消和可观测资源回收；测试阶段不开放生产访问。
- 用模拟上游隔离网关开销，再测指定真实模型。先测直连 vs Java；如需宣称 Java 优于 FastAPI，再加等价 Python 代理对照，预计额外 2–4 人日，不修改 `lithe-api`。
- 记录 JAR 在目标等效环境运行的证据。没有 M1 性能与协议证据，不进入完整平台化开发。

### I2：课题与公司身份不能补丁式加入

- 设计课题、公司授权、部署身份、模型资源的公开契约及数据结构。执行现有数据库 Skill/规范；需要标准 CRUD 时从 `vita-generator` 模板生成。
- 实现一个逻辑课题 Key 和轮换版本；一个部署的公司/环境可信绑定；多课题共享进程下上下文隔离。
- 策略发布校验、原子版本切换及撤销时限。不可用的身份校验依赖采用拒绝策略。
- 加入被动观测、低成本探测和小型推理探测，独立展示状态与过期时间。
- 管理查询的公司权限以真实服务端过滤验证；平台组织体系未就绪时使用经核准的公司映射，不声称已经完成全集团 IAM。

### I3：完整负载与失败路径

- 多实例同时发起请求，验证准入的原子性、各维度交集、租约续期/释放/过期及过载拒绝。
- 生命周期事件、持久暂存、幂等重放、聚合和未知 usage 标识形成闭环。
- 注入模型超时、慢读、半开连接、客户端断连、Redis 故障、DB 中断、磁盘水位、进程退出及重复事件。
- 完整功能开启后复测 NFR-01，执行 24 小时持续运行，量化暂存与崩溃造成的数据窗口。
- 使用合成输入，故障注入不直接施加到生产共享依赖。

### I4：真实业务先单点验证

- 最小 `web-ele` 管理界面完成申请、审批、模型/公司授权、Key 轮换、部署停用和健康/用量查询。
- 对试点所有模型调用路径做清单，既包含公共入口，也包含业务内部直接调用。
- 接入由业务代码维护者在实际受管项目实施；本地 `lithe-api` 继续只读，不纳入本仓库版本管理。
- 配置驱动切小流量，记录超时、业务结果、Token 与错误；完成一次受控回滚再恢复网关路径。

### I5：验证推广模型成立

- 为公司 B 登记独立部署身份，并授权同一个课题 Key；使用可区分的合成请求量核对 A/B 汇总。
- 禁用 A 的公司授权或部署，验证 B 正常；伪造公司头、使用未授权部署均失败。
- 验证集团授权汇总与公司局部查询，覆盖列表、合计、详情及导出。
- 验证同进程不同课题、相同课题不同公司部署及重叠 Key 轮换无归属串线。

### I6：可交付、可恢复、可运维

- 使用完整发布候选制品执行 72 小时测试，并保留原始监测数据与资源曲线。
- 双实例滚动发布/故障切换，明确在途 SSE 的失败边界；入口、Redis、数据库若仍单点需记录，不能写“全链路高可用”。
- 实测配置、凭据、统计数据的备份恢复和制品回滚；迁移脚本说明兼容性及回退方式。
- 输出分批推广计划：已试点公司 → 少量下一批 → 其余公司；每批观察后人工决定继续或回滚。M6 不自动授权一次性切换全部 8 家公司。

## 4. 延后需求及进入条件

| 后续能力 | 开始条件 |
| --- | --- |
| 严格 Token 预算/计费 | usage 覆盖率和取消语义满足要求，明确预留/结算与缺失策略，单独验收 |
| embeddings、rerank、音频等 | 有真实课题需求及上游能力样本，分别补充协议、统计和性能基线 |
| 自动跨模型回退 | 业务确认结果语义、数据范围和费用变化，可追踪且可关闭 |
| 更完整的审批和 SSO | 集团基础身份体系达到对接条件，不在网关重复建设员工体系 |
| GPU 运行级监测 | 上游提供指标并校验版本，区分模型队列与网关在途数 |

## 5. 变更与验收规则

每次修改范围、阈值、身份方案或持久性承诺，都记录原因、影响和需重跑的验收项。通过后改动转发、资源控制或依赖版本，必须重跑相关性能/稳定性项；纯文档修订不要求重复全套压测。

里程碑材料不完整时保留待验收状态。限范围通过必须写清允许的下一步、禁止扩大范围、风险责任人和补验日期，不能借此跳过公司隔离、协议正确性或关键资源泄漏问题。
