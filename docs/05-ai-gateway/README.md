# 企业 AI 网关规划

版本：0.1 草案 · 日期：2026-11-13 · 状态：**待 M0 人工评审，尚未实现网关或进行性能测试**。

## 当前结论

推荐在现有统一仓库中新增独立部署的 Java AI 网关，候选模块为 `backend/vita-ai-gateway`。转发层采用 Spring WebFlux + Reactor Netty；平台继续承担管理端登录、权限和配置管理。不要把长连接转发嵌入 `vita-admin` 或某个部门业务应用。

仅比较性能和稳定性，也优先选择上述 Java 非阻塞方案。这是针对持续运行、流式连接和集中资源控制的工程判断，**不是 Java 已经实测优于 FastAPI 的结论**。两者的具体差距由 M1 验证；完整功能加入后的性能由 M3、M6 再验证。

## 已确认的需求

- 上游为公司本地部署的 OpenAI 兼容模型接口；现有 FastAPI 业务服务逐步统一通过网关调用。
- **按课题申请一个逻辑 API Key**，不是按模型服务发 Key。一个课题可授权多个模型，并逐步推广到不同分公司。
- 必须区分同一课题在不同公司的调用；公司默认隔离，集团和跨公司岗位按授权查看。
- 优先保证低开销转发、模型健康检测、稳定和快速，同时具备请求量、Token、流量、并发的基本监测。
- 采用 Java 可在本地打包、线上运行的交付方式；部署便利性不作为性能和稳定性比较的论据。
- `lithe-api/` 仅作本地业务参考，不纳入 Git，不在本轮修改。

## 使用约定

本专题的需求以 PRD 为准，测试阈值在 M0/M1 冻结。所有里程碑当前均未通过；用户验收后才进入依赖该里程碑的下一阶段。该验收安排来自用户要求的人工介入点，不代表已经获得上线批准。
