# 集团基础框架需求

## 已确认背景（2026-11-12）

- 集团下有 8 家分公司，默认相互隔离；集团及跨公司岗位按明确授权访问。
- 同一员工使用一个账号，支持跨公司、多部门任职，各任职可拥有不同权限。
- 先完善账号密码登录，预留企业 SSO；保留国际化能力。
- 平台提供身份、组织、权限和公共能力。`vita-ah-waste`、`vita-gm-purchase`、`vita-gm-mailrec`、`vita-cw-aiaudit` 分别承载部门业务，逐步实现独立部署和迭代。

## 分批交付与验收

| 批次 | 交付内容 | 验收条件 |
| --- | --- | --- |
| 1：鉴权基线（本次） | 有效账号检查；取消跨请求 RBAC 缓存；过滤停用角色；固化集团模型 | 已登录用户停用后受保护接口拒绝；角色/权限/关联撤销提交后的新请求失权；查询指定用户权限不串用当前请求用户 |
| 2：身份与组织 | 公司、部门归属、多任职、当前任职选择；密码存储与重置、会话撤销完善 | 同一账号可在授权任职间切换；无效或他人的任职不可选择；公司停用阻断其任职；迁移现有单部门数据 |
| 3：授权与数据边界 | 任职角色授权、授权管理边界、按操作解析公司及部门范围 | A 公司可编辑、B 公司只读时，B 公司编辑被拒绝；猜 ID、列表、统计、导出、附件、批量写和子表均不能越界 |
| 4：独立业务接入 | 平台身份与授权契约、业务侧鉴权组件、数据归属、首个真实业务样例 | 一个业务升级无需重启其他应用；无权直接调用业务 API 被拒绝；依赖故障默认拒绝访问 |

本次不建公司表、不迁移组织数据、不改变现有账号密码、不接入 SSO。当前的 `tenant_id`、`dept_id`、`data_scope_type` 字段不代表公司数据隔离已经实现。第 3 批完成前，不可用现有平台承载要求公司隔离的真实业务数据。

## 关键验收场景

1. 员工在公司 A 采购部和公司 B 财务部各有任职；撤销其中一个任职不影响另一个，权限不能混用。
2. 集团采购岗获 A/B 公司采购查看权限，不能查看 C 公司，也不能因此查看 A/B 的财务业务。
3. 同一人持有 A 公司采购编辑和 B 公司采购查看授权，不能将编辑权限与 B 公司范围拼接。
4. 未授权账号修改请求中的公司、部门、任职或主单 ID，服务端必须拒绝；子表从已授权主表继承归属。
5. 部门业务独立发布；业务应用不读取平台内部数据库，不共用平台 JWT 签名密钥或 Session 序列化格式。

设计依据见 `docs/architecture/system/group/group-foundation-design.md`。
