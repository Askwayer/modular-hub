# 集团身份、授权与业务边界

需求依据：`docs/requirements/group-foundation.md`。本文件描述目标模型与实施顺序；除“本批实现”外均为待实现设计。

## 模型决策

| 概念 | 职责与约束 |
| --- | --- |
| 账号 `sys_user` | 员工唯一身份；账号状态作用于所有任职。账号不直接拥有唯一公司，现有 `dept_id` 后续迁移为任职关系 |
| 公司 | 数据归属与授权范围的基本单位；8 家为当前业务背景，不写死数量。集团管理机构及公司层级不自动产生下级访问权 |
| 部门 `sys_dept` | 必须归属公司；部门父子关系不能跨公司。组织部门与代码中的业务应用不是一一对应关系 |
| 任职 | 账号 + 公司 + 部门 + 岗位，具有状态、有效期及主任职标识。主任职仅用于默认展示，不授予额外权限 |
| 角色 | 功能权限模板；岗位是组织职责，角色是授权集合，两者分开 |
| 授权 | 将任职、应用、角色、公司集合和公司内的数据范围绑定为一条授权；可有生效/失效时间及授权审计 |
| 企业身份绑定 | 后续按身份提供方和稳定主体标识绑定账号；不按可变用户名/邮箱自动合并。SSO 验证身份后仍走相同任职及授权规则 |

`tenant_id` 保留为租户维度，不借用来表示分公司。本集团当前公司边界由明确的 `company_id` 表达；以后如果引入多集团租户，还需要独立的租户边界。

## 请求上下文与授权计算

登录确认账号；后续选择任职必须由服务端校验归属、状态、有效期及公司/部门状态。客户端传入的公司或任职 ID 只是请求参数，不是可信上下文。跨公司查询仍需显式指定目标或请求授权范围内的集合。

授权判定以 `(账号, 当前任职, 应用, 操作, 目标资源)` 为输入：

1. 确认账号、任职、公司及授权有效。
2. 只保留包含本次操作的授权。
3. 在每条授权内计算公司范围与部门/本人/自定义范围的交集。
4. 对这些完整授权结果取并集，再与业务条件取交集；没有授权则拒绝。

不能分别汇总所有角色权限和所有公司范围再做笛卡尔积。例如：A 公司编辑 + B 公司查看，只允许编辑 A。当前 `data_scope_type=ALL` 未来应解释为该条授权所选公司的范围，不是集团无限制访问。

公司外层边界始终生效。集团岗位通过明确的公司集合授权；新增公司不自动进入既有授权。授权管理本身也要受范围约束，管理者不能授予自己没有管理权的公司、应用或角色。当前超级管理员为平台维护入口；接入真实业务前必须明确业务数据访问的受控例外及审计，不把现有通配权限视为默认跨公司业务权。

## 数据模型与访问约束

- 业务主表保存不可由普通更新任意改变的 `company_id`，需要时保存归属部门、负责人。任职变化不追溯改变历史业务归属。
- 子表通过主表归属校验读写；如冗余公司字段，必须与主表一致，并在事务内校验。
- 详情、更新、删除先使用授权范围查询目标；批量操作整批校验，任一越权默认整体失败。
- 列表、分页总数、KPI、导出使用相同范围；关联查询和附件下载不能只校验主入口。
- `TenantLineInnerInterceptor` 或数据权限拦截器只能作为持久化执行机制，不能替代授权模型。自定义 SQL、异步任务、定时任务需要明确的服务身份和范围；缺少范围不能解释为全部。
- SQL 迁移应保持现有数据，先明确现有员工和部门的真实公司归属，禁止猜测批量填入某家公司。新增 CRUD 按仓库生成器规范生成。

## 应用与部署边界

平台继续采用 `vita-admin -> vita-service -> vita-common`；四个业务应用保留独立入口、制品、配置和数据迁移。业务包按业务能力归属，不按 8 家公司复制 8 份代码。

业务应用通过版本化的身份/授权公开契约获取上下文，不依赖整套 `vita-service`，不直接查询平台 IAM 表。接入企业身份系统前先验证其协议与账号绑定方式；不提前自建 SSO 服务。SSO 不代替业务授权。公共组件使用可选版本升级，不能要求某业务更新时所有应用同时发布。

当前四个 `/module/name` 仅为匿名打包测试接口，尚未接入上述身份与数据权限。国际化、日志、文件、验证码等能力保留；文件对象授权和可靠审计需随业务接入补齐。

## 本批实现与限制

- 请求链路按顺序执行：请求跟踪 → 实时加载有效账号 → Sa-Token 登录及权限校验 → Controller。
- 有效账号来源为启用且未删除的 `sys_user`；权限回调始终按传入 `loginId` 查询，未知账号域及非法 ID 拒绝授权。
- 用户角色、角色权限、角色菜单关联与目标角色均须有效；启用权限、菜单才产生结果。
- 取消 Session 中用户资料、角色码和权限码的读取与写入，避免旧快照继续赋权；Sa-Token 本身的令牌生命周期机制仍保留。
- 授权修改提交后，后续鉴权查询读取新状态。已在执行中的请求不追溯中断；本批不实现禁用再启用、密码重置后的全终端会话撤销。
- 当前阶段增加数据库读取次数，优先确保撤权正确；后续优化需有版本校验、明确失效时限及故障拒绝规则，并先测量性能。
- 本批不改变表结构，无数据库升级脚本；不宣称多任职、公司隔离或独立业务鉴权已经落地。
